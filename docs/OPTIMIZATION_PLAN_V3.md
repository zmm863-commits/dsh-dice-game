## 一、现状核实：联机代码到底能跑到哪一步

联机代码完整保留但被封面短路（`MP_DISABLED = true`，`index.html:4289`）。逐条实测结论：

| 环节 | 证据（index.html） | 实测结论 |
|---|---|---|
| 封面入口 | `4783-4786` | `MP_DISABLED` 为真 → 点击「开始游戏」直接 `mpStartSingle()`，模式弹窗永不出现 |
| 深链 | `4765-4779` | `?room=` / `__DICE_INIT_ROOM__` 被 early return 忽略；恢复后也只「打开弹窗+预填」，不自动加入 |
| 房间号 | `4391-4398` | 32 字符集 6 位（去掉 I/O/0/1）≈1.07e9 空间，强度足够；**无频率限制、无口令、无租约** |
| 信令 | `4415-4424` / `4484-4493` | PeerJS 公共 cloud wss + 3 个 Google STUN，**无 TURN** |
| 消息面 | `4586-4605` | 只有 3 种：`dice` / `bid` / `challenge` |
| 死代码 | `4573` / `4576` | `new_round`、`select_mode` 有 case **无任何发送方**（全文件检索确认） |
| 房间切换 | `2691-2721` | `switchMode` 纯本地 + `resetGame()` + 弹规则，**不广播** → 双方模式必然不一致 |
| 回合归属 | `2879` | `currentTurn = mpIsHost ? 0 : 1` → 房主**每局永远先手**，先手优势恒定 |
| 死变量 | `4295-4297` / `4550` | `mpMyTurn` 声明后从未使用；`mpOpponentDice` 只写不读 |
| 断线 | `4635-4660` | 只有文案 + 10s 后弹窗；**无 `peer.reconnect`、无 conn 重建、无重 join 令牌** |
| 断线后果 | `4647` / `4651` | 10s 后 `mpGameActive=false` 且恢复 `cheatBtn` → **游戏静默退化成单人**（对手区仍显示「好友」，行为却变 AI） |
| 结算 | `5279` `5281` `5356` | `isMp` 门控 → 联机全程**不发骰币、不计 wins/losses、不计 perMode、不推任务** |
| 联机唯一计分 | `3249-3256` 等 5 处 | 会话内 `playerWins/computerWins`，不落盘 |
| 道具 | `4609-4611` | 只隐藏 `cheatBtn`，**未隐藏 `itemBar`**（`1659-1663`） |

**一句话结论**：联机是「能连上、能对局、但语义与记账全缺」的半成品；且有三处会**必然**造成不同步或作弊（道具重掷、模式本地切换、道具偷看）。

## 二、A 系列：联机（用户要求的方向）

### A0【P0】可达性形态判定：联机在什么部署形态下成立 —— 难度 S

- **现状证据**：`4307-4336` `mpGetPublicBase()` 三级取址（宿主注入 `window.__DICE_PUBLIC_BASE__` → URL `?diceBase=` → `localStorage.dicePublicBase`）；`mount.ts:58-62` 只把 GUI URL 的 `diceBase` 透传进 iframe，**宿主默认不注入**；`4359-4388` 无 `joinUrl` 时降级为房间号卡片。
- **问题**：DSH 内嵌默认形态下，游戏托管在本地 `/dice-game/` 路由，`joinUrl` 恒为空 → **二维码/邀请链接永远不可用**，但 UI 仍把二维码白框（`1551-1558`，160×160 固定高）和「📤 发送给好友」（`1560`）当主入口，玩家看到的是一个空框。
- **建议方案**：
  - **形态 A（无 diceBase，默认）**：创建房间页改为「房间号专用」——大号 6 位分组码（`ABC-123`）+ 一键复制 + 三步图文（在你自己电脑上打开骰子大作战 → 加入房间 → 粘贴房间号）。移除二维码白框占位。
  - **形态 B（有 diceBase）**：保留二维码 + 链接分享。
  - 两形态由 `mpBuildJoinUrl() !== ''` 单点判定，复用已有分支框架。
  - 补充认知：DSH→DSH 双机对战时，双方各自本地打开插件、**手动传码**才是唯一的真实可用路径（信令走公网 wss，不受 opaque origin 限制）。UI 应默认按这条路径设计，而不是按「扫码」设计。
- **改动范围/成本**：仅 `index.html`（`mpRenderRoomShare` + 创建页 DOM/CSS），S。
- **验收方式**：jsdom 注入 `mpGetPublicBase()===''`，断言 `#mpQrCode` 内出现房间号文本且不含 QR 容器；注入 `?diceBase=` 后断言走 QR 分支。

### A1【P0】房间入口信息架构：三平权选项 → 两层决策 + 上次房间记忆 —— 难度 M

- **现状证据**：`4783-4810` 封面点击 → `mpModeOverlay` 三选一（单人/创建/加入，`1526-1540`）；`4788-4792` 「取消」= **静默 `mpStartSingle()`**；无任何房间记忆。
- **问题**：
  1. 单人（主玩法）与联机（社交玩法）平权并列，新玩家默认点第一个；
  2. 「取消」语义欺骗——玩家以为回到封面，实际已进入单人局；
  3. 房间号记不住，每次重新输入（好友局通常要连打好几局）。
- **建议方案**：
  - 两层化：主 CTA「▶ 继续单人」+ 次 CTA「👥 和好友玩」；点后者才展开「创建房间 / 加入房间」。
  - 「取消」改为**返回封面**（不进入任何模式），并把「单人」明确标注为默认路径。
  - 新增持久化键 `dice_last_room`（记住最近一次成功加入的房间号，含时间戳），加入弹窗预填 + 提供「重连上次房间」按钮。
- **改动范围/成本**：`index.html`（弹窗 DOM + `mpBindEvents`）+ **新增白名单键需同步三处**：`DiceStore.KEYS`（`4853`）、宿主 `DICE_SAVE_KEYS`（`mount.ts:66-76`）、`smoke-p0 [G]` 白名单断言。M。
- **验收方式**：断言「取消」后 `#coverPage` 未加 `hidden`；断言预填值等于上次房间号；断言宿主侧白名单含 `dice_last_room`。

### A2【P1】创建等待页：从「死等」到「可感知」 —— 难度 S-M

- **现状证据**：`4426-4436` 仅一个 15s 超时文案；`4433-4436` 成功后只改一行状态字；`4391-4398` 房间号一旦创建即固定；`4812-4815` 取消才 `peer.destroy()`。
- **问题**：玩家不知道房间还能撑多久、好友有没有收到码、当前卡在哪一步；房间号无法主动换新。
- **建议方案**：
  - **三步握手可视化**：`信令已连接`（`peer.on('open')`）→ `正在打洞`（`peer.connect` 已发起）→ `已连接`（`conn.on('open')`），每步点亮/转圈，失败步标红并给可执行动作。
  - 房间时效提示（**[待验证]** 建议租约 30 分钟，与房间号生命周期绑定）+「🔄 换一个房间号」+「❌ 关闭房间」。
  - 等待中显示已等待秒数，超过 30s 给「把房间号复制发给好友」的加强提示。
- **改动范围/成本**：`index.html`，S-M。
- **验收方式**：jsdom 模拟 `peerOpen` / `connOpen` 事件，断言三步状态推进；断言超时后出现「重试/换号」按钮。

### A3【P0】对手状态可见性 + 轮到谁的提示（联机专属回合 UI） —— 难度 M

- **现状证据**：`2954-2955` 状态文案写死「等待电脑…」；`3060-3064` 「电脑正在思考…」；`1637` 对手头像固定 🤖；`4614` 只改了 `.player-name`；`1601` 连接状态是**静态** HTML；`2879` 房主恒先手；全场无回合计时器。
- **问题**：联机下玩家读到的是 AI 话术（认知错位）；对手「已选好数字」这种关键中间态不可见；无计时 → 可无限拖延；房主恒先手是隐性不公平。
- **建议方案**：
  - **称呼统一**：引入 `oppName()`（返回「电脑」/「好友」）与 `isMp` 分支词条，替换 `2954-2955`、`3060-3064`、`3234`、`3916`、`4067` 的写死「电脑」。
  - **对手状态机**（轻量非权威）：`思考中 / 已选好 / 已叫点 / 已开盅`，由新的 `mpSend({type:'presence', state})` 驱动；对手状态直接显示在其头像下方（复用 `#computerStatus`）。
  - **回合倒计时**（**[待验证]** 建议 30s）：环状进度 + 「你还有 Ns」；超时策略二选一（自动过/本回合判负），必须**文案明示**、不可静默。
  - **先手轮换**：改为「上一局败者先手」或每局交替（`currentTurn` 由局号奇偶决定），消除恒定先手。
  - 双人配色区分（你=蓝 `#60a5fa`、好友=橙 `#fb923c`），复用现有 `.score-dot.p/.c` 色语言。
- **改动范围/成本**：`index.html`（`startBidding` + `updateUI` + 新消息类型 + CSS），M。
- **验收方式**：断言存在 `presence` 消息处理分支且 UI 文本随之切换；断言计时器启动/超时回调存在；断言非房主也能先手（连续两局 `currentTurn` 不同）。

### A4【P0】断线 / 重连 / 对手离开：把「重连中…」变成真的 —— 难度 M

- **现状证据**：`4635-4660` 全文只有文案与一个 10s `setTimeout`；`4654-4656` 弹窗文案「可刷新页面重新联机」；`4647` `mpGameActive=false` + `4651` 恢复 `cheatBtn` → 静默降级为单人；无心跳。
- **问题**（三个独立伤害）：
  1. `4636-4638` 承诺「尝试重连…」，但**没有任何重连代码**——空头承诺直接损害信任；
  2. 10s 后游戏静默转单人，对手区仍显示「好友」而实际由 AI 接管 → 一局结果无归属，玩家体验断崖；
  3. 无「对手离开 → 本局判胜/判无结果」规则。
- **建议方案**：
  - **连接状态条**（复用 `#mpConnectionStatus`）：`🟢 已连接 / 🟡 重连中 (剩余 Ns) / 🔴 已断开`，由**心跳**驱动（§B）。
  - **宽限期内冻结输入而非放手**：宽限期（**[待验证]** 建议 60s，与 v1 §六一致）内所有操作按钮 `disabled` + 遮罩提示「对方网络不稳定，等待重连」，**不**把控制权交给 AI。
  - **宽限超时**：结算弹窗定性为「对手掉线」并给两个明确出口——「结束本局（判你胜/无结果）」+「留在房间等对方重进」（后者依赖 §B 的房间租约）。
  - **严禁 `4647` 式静默降级**：若玩家要转单人，必须是显式选择。
  - 断线时清空本地待发队列并提示「你刚才的动作未送达」。
- **改动范围/成本**：`index.html`，M（真正重连需 §B 配合）。
- **验收方式**：模拟 `conn.on('close')` → 断言状态条进入重连中、输入禁用、出现倒计时；推进 60s → 断言出现「对手掉线」结算且**不存在**继续单人局的路径。

### A5【P0】联机专属结算与记账分区：从「数据黑洞」到「有归属」 —— 难度 M-L

- **现状证据**：
  - `5279` `var isMp = mpGameActive === true`；`5281` `if (winner === 0 && !isMp)`；`5356-5376` `if (!isMp) { … }` → 联机不发骰币、不计 `stats.wins/losses`、不计 `perMode`（`5336-5338`、`5372-5374`）、不推任务（`5342-5347`）。
  - 但 **AI 话术照旧**：`3250/3254`、`3454/3456`、`3594/3596`、`3813/3815`、`3931/3935`、`4085/4089` 全部 `aiBluffLine('lose'/'win')` + 「😅 电脑赢了」；`3271`、`3470`、`3610`、`3829`、`3953`、`4108` 弹窗标签硬编码 `'你'`/`'电脑'`。
- **问题**：赢了朋友的玩家看到「🤖 AI > 人类」；同时联机战绩完全不累积 → 打联机 = 生涯空转，长期无意义。
- **建议方案（这是「如何共存」的正面回答）**：
  1. **结算文案分流**：`isMp` 时用「你 / 好友」+ 好友名字，去掉 `aiBluffLine`，emoji 改 🤝/🎉；弹窗骰子行标签用 `oppName()`。
  2. **记账分区【已定案 2026-09-27】**：联机独立成账 —— 新增 `dice_stats_mp`（局数/胜负/最长连胜/系列赛记录），生涯面板 `showStats`（`5770-5807`）增「联机」一栏；**不复用** `dice_stats.coins`、不推单人每日任务、不影响 `RANK_LADDER`（`5399-5413` 由 `payoutTotal` 驱动，只增不减，被联机污染后会失真）。
  3. **联机筹码独立**：局内押注双方**回合前锁定同额**，胜者得全额（零和），与单人彩金池隔离 —— 避免出现「联机印钞 → 单人段位与商店通胀」的无限刷分回路（v1 §一 的设计红线）。
  4. **已定案（用户 2026-09-27）：联机不产出任何单人资源。** 骰币、段位、每日任务三者与联机完全绝缘，联机只累积 `dice_stats_mp` 与联机徽记。因此上面第 2 条的记账分区是**唯一正确实现**；「设每日联机收益封顶」的备选路径**作废**，不再保留。
  5. 联机专属奖励：不给骰币，给**联机徽记**（如「连胜好友 3 局」），与 P3-2 成就墙共用载体。
- **改动范围/成本**：6 处 reveal 结算块 + `onSettle` + `showStats` + 任务口径，M-L。
- **验收方式**：jsdom 置 `mpGameActive=true` 后触发各玩法结算 → 断言 `dice_stats` **无变化**、`dice_stats_mp` 递增、任务进度不推进、结算文案与骰子标签无「电脑」字样。

### A6【P0】公平性与防作弊：界面侧先止血 —— 难度 S（止血）/ M（道具改造）

- **现状证据**：
  - `4609-4611` `mpStartGame` 只隐藏 `cheatBtn`，**未隐藏 `itemBar`**（`1659-1663`）。
  - `5849-5854` `peek`：直接 toast 出**对手真实骰子值** —— 联机下这就是偷看（`computerDice` 在 `4551` 已被写入真值）。
  - `5855-5861` `reroll`：在 `mpSendDice()`（`2826`）**之后**本地 `rollDice()` → 双方骰面不一致，开盅判定必然分叉。
  - `5862-5864` `shield`：只在单人分支生效（`5363`）→ 联机买了个没用的道具。
  - `1619-1625` `betSelector` 在联机仍可选，但 `5328`/`5367` 只在单人分支结算 → 押注无效。
- **问题**：道具栏在联机 = 作弊器 + 不同步制造机；押注器 = 无效果的假控件。
- **建议方案**：
  - **止血（一行级）**：`mpGameActive` 时隐藏 `#itemBar` 与 `#betSelector`，换成联机专用两个按钮（表情 / 认输）。
  - **若要保留道具**（后续）：`reroll` 必须「双方确认 + 重新广播骰子快照」；`peek` 在联机**永久禁用**（信息不对称即作弊）；`shield` 需在联机结算分支接入。
  - **可信度可视化**：开盅时同时展示**双方全量骰子快照**（扩 `createDiceRowHTML`），并在等待/开局时显示「本局骰子已封存，开盅同时揭晓」——用界面表达规则公平，比口头承诺有效。
  - **权威化属技术层**（§B）：只要骰子由客户端本地生成并先行广播，作弊面就堵不住；本节只解决「用现成 UI 就能作弊」的显性漏洞。
- **改动范围/成本**：止血 S；道具改造 M。
- **验收方式**：断言 `mpGameActive` 时 `#itemBar`、`#betSelector` 为 `display:none`；断言联机路径下 `peek` 不产出对手骰值。

### A7【P0】加入体验细节：粘贴整段邀请 → 必须能自动提取 —— 难度 S

- **现状证据**：`1573` `<input maxlength="6">`；`4470-4474` 仅校验 `length < 4`；`4665-4668` 复制的邀请文本是 `🎲 骰子大作战 房间号：${code}`（**带中文前缀**）；`4817-4819` `mpJoinClose` **未** `peer.destroy()`（对比 `4812-4815` 创建侧有）；`4505` `peer.connect(code)` 无格式校验。
- **问题**（这条是**必然踩到**的坑）：
  1. 好友按提示复制了分享文案，整段粘进 `maxlength=6` 的输入框 → 被截断成「🎲 骰子大」→ `connect` 必然失败，且失败文案（`4536`）还说是「房间不存在」→ 玩家怪房间号错了；
  2. 关闭加入弹窗泄漏一个 PeerJS 实例（重复点击会累积）。
- **建议方案**：
  - 新增 `mpExtractCode(text)`：正则提取 `[A-Z2-9]{6}`（26+6 字符集，去掉易混字符），从任意邀请文本/URL 中还原房间号；`oninput` 过滤非法字符 + 自动大写 + 6 格分组视觉（`ABC-123`）。
  - 粘贴事件直接提取并回填，附带「已从邀请文本中识别房间号」提示。
  - 加入失败文案可执行化：「房间不存在」之外补「确认大小写 / 确认对方未关闭房间 / 换新房间号」。
  - `mpJoinClose` 补 `peer.destroy(); peer = null;`，并保证「同一时刻至多一个 peer 实例」。
- **改动范围/成本**：`index.html`，S。
- **验收方式**：断言 `mpExtractCode('🎲 骰子大作战 房间号：ABC123') === 'ABC123'`、`mpExtractCode('…?room=ABC123') === 'ABC123'`；连续点击加入 3 次后活动 peer 数 ≤1。

### A8【P1】社交层：固定表情 / 快捷语（不做自由文本） —— 难度 S-M

- **现状证据**：`4579-4581` `case 'chat': // 可扩展聊天` → 空实现；`5676-5694` `AI_BLUFF` 已有 8-10 条 × 4 类现成句式（zh/en 结构可复用）。
- **问题**：真人联机却没有最低限度的社交表达；面对好友的「运气好」无处表达，只剩沉默。
- **建议方案**：
  - 6-8 个**固定表情/快捷语**（`👍 服了` / `😅 运气` / `🎲 再来` / `🤔 想想` / `😈 你敢开吗` / `GG`），复用 `AI_BLUFF` 句式与中英双语词条体系。
  - 气泡显示在对手头像旁（200ms 淡入淡出），本端发送后按钮进冷却（**[待验证]** 建议 3s），防刷屏。
  - **不做自由文本**：无审核能力、无意义、且易用于侮辱。
- **改动范围/成本**：`index.html`（消息类型 + 气泡 UI + 冷却），S-M。
- **验收方式**：断言 `chat` 消息渲染气泡且文案来自词条字典；断言冷却期内重复发送被拒。

### A9【P1】邀请与分享：把「复制 → 粘贴 → 自动提取」闭环打通 —— 难度 S

- **现状证据**：`4663-4694` 四级降级（`wx.miniProgram` → `navigator.share`（`4676` 要求 `!mpIsEmbedded()`）→ 复制链接 → 复制房间号）；`4691` 无链接时文案为「打开骰子大作战 → 加入房间 → 输入房间号」。
- **问题**：DSH 内嵌下 `navigator.share` 被 `mpIsEmbedded()` 挡掉，只剩复制；但复制文案与 A7 的输入框不兼容；按钮文案「📤 发送给好友」承诺了做不到的系统分享。
- **建议方案**：
  - 统一邀请文案模板：房间号置顶 + 6 位分组 + 三步操作 + 时效提示（与 A2 一致）。
  - 无 `joinUrl` 时按钮文案改为「📋 复制邀请文本」（诚实设计），有 `joinUrl` 才显示「📤 分享给好友」。
  - 与 A7 的 `mpExtractCode` 组成闭环：任何形态复制的文本都能被任何形态的输入框吃下。
- **改动范围/成本**：`index.html`，S。
- **验收方式**：断言 `mpShareRoom` 在无 `joinUrl` 时写入剪贴板的文本可被 `mpExtractCode` 反解出同一房间号。

### A10【P1】赛制与「再来一局」：从无限局到有终点 —— 难度 M

- **现状证据**：全文件检索 `rematch` / `bestOf` / `再来一局` / `系列赛` = **0 命中**；`roundBadge`「第 N 局」是会话内自增（`2760`、`3107`、`3170` 等）；`4573/4576` 的 `new_round`/`select_mode` 无发送方 → 双方各自点「开始新局」会各掷各的骰子、各涨各的局数。
- **问题**：没有赛制 → 不知何时算「这一场」结束；没有就绪握手 → 局数与模式可能各自漂移；没有重赛仪式感。
- **建议方案**：
  - **已定案（用户 2026-09-27）：联机赛制为「先到 N 胜」**，N 默认取 **5**（**待实测校准**，实现为单个常量便于调整）；顶部显示 `你 3 — 2 好友` 的赛制进度条，替代纯「第 N 局」。
  - 「🔁 再来一局」改为**双方就绪握手**（双绿勾才开局），把 `new_round` 变成真实消息。
  - **模式切换需双方同意**：`switchMode` 在联机下改为发起请求 + 等待确认，落地 `select_mode` 消息（修掉 `2691` 的本地切换不同步）。
  - 赛末出**系列赛小结**（总比分、最长连胜、最佳单局），复用 A5 的 `dice_stats_mp`。
- **改动范围/成本**：`index.html`，M。
- **验收方式**：断言点击「再来一局」后本端进入「等待对方就绪」态、比分未重置；断言联机下 `switchMode` 不直接重置本局，而是发出请求。

### A11【P2】联机复盘（对 P3-5「AI 观战回放」的增补） —— 难度 M

- **现状证据**：无任何回放/记录实现（P3-5 已规划为教学向 AI 回放）。
- **增补点**：**联机复盘比 AI 回放价值更高** —— 记录每局叫点序列 + 开盅全量骰子快照，用于「上一局到底几颗红」的争议复盘，同时也是防作弊的可视证据链。技术上是 P3-5 的同一份记录设施，只是入口挂在联机结算面板上。

### C3【P0】每日任务：时区错位 + 封顶失效 + 与设计稿不一致 —— 难度 S

- **现状证据**：
  - `5428` `var today = new Date().toISOString().slice(0, 10)` → **UTC 日期**；东八区玩家在**早上 08:00** 而非 0 点刷新任务。
  - `5388-5395` 6 条任务全量下发；奖励合计 50+30+30+80+60+40 = **290** < `DAILY_REWARD_CAP = 450`（`5396`）→ **封顶永不触发**，「防刷红线」形同虚设。

## 七、原需决策的两个问题 —— 已定案（用户 2026-09-27）

1. **联机对局是否产出单人资源（骰币/段位/每日任务）？** → **定案：不产出。** 联机独立成账（`dice_stats_mp`）+ 独立徽记；单人骰币、段位（`RANK_LADDER`）、每日任务三者与联机完全绝缘，从根上切断「联机印钞 → 单人通胀」的回路。
2. **联机赛制**：无限局还是「先到 N 胜」？ → **定案：「先到 N 胜」。** N 默认取 **5**，实现为单个常量，待真机对局数据回收后校准。该赛制同时回答「何时算一场结束」与「再来一局的仪式感」。

> 结论：A5 与 A10 由「阻塞」转为「可实施」；A5 的实现路径随之唯一化（记账分区），A10 的 N 值待实测校准。
